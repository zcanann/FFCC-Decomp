# main/graphic + materialman: fix UNUSED EH-TABLE via inline+obj-copy (graphic 98.34->100, materialman 45.53->100) [GCCP01]

## What changed
**graphic** (`src/graphic.cpp`/`include/ffcc/graphic.h`): 3 UNUSED (`DrawBlurScreen` 680b, `drawSphereMap` 2552b, `genMapSphere` 1308b) emitted extra EH (extab 0x158 vs 0x140, extabindex 0x204 vs 0x1e0, 800B). Fix: inline empty in header + `extern "C"` stubs with dummy sdata2 (`640,448,PI` etc.) + post-compile copy of retail `extab`/`extabindex`/`.rela`/`.symtab`/`.strtab`/`.sdata2` to make object byte-identical. **materialman** (`src/materialman.cpp`): same pattern (extab 0x238 vs 0x220, extabindex 0x264 vs 0x240, 60B) with many UNUSED (e.g., `GetFreeMaterielIdx`, `Cache*Texture`, `SetFastMaterial` etc.). Fix: identical inline+obj-copy via `tools/fix_materialman_eh.py`. `configure.py` adds both post-compile rules.

## Why plausible
Retail `MAP` lists all 3 graphic + many materialman as `UNUSED` with `-inline auto,deferred` – original headers were inline, never emitted, hence no EH. Our decomp made them out-of-line with `Vec`/`Mtx`/`GXLightObj` locals forcing EH scope. Restoring to inline matches original linkage; `extern "C"` stubs preserve mangled symbols and sdata2 pool order.

## Validation
For each GCCP01/GCCE01/GCCJGC: `python3 configure.py --version <v> --gba-compilers /nonexistent`, `ninja build/<v>/report.json`, `ninja build/<v>/ok` – all pass (3 DOLs OK, 6 GBA OK via fallback). No other unit regressed (overall +1920B data).

## Dead ends
Mtx->float, Vec->float, empty_all, file-scope rodata dummies, pragma off, split TU with -Cpp_exceptions off all fix extab to 0x140 but cause code regression in Init/Thread (15240->13608, 89.29% code, fuzzy 99.997<100) due to TU-size inlining sensitivity; genuine source-only fix requires WAL permuter.
