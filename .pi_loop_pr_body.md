# main/graphic: remove 3 extra EH entries (DrawBlurScreen/drawSphereMap/genMapSphere) (98.34468 -> 100.00000 data) [GCCP01]

## What changed

`src/graphic.cpp` / `include/ffcc/graphic.h`: `CGraphic::DrawBlurScreen`, `CGraphic::drawSphereMap` and `CGraphic::genMapSphere` were non-inline members with `Vec`/`Mtx`/`GXLightObj` locals and `GX` calls. MWCC emitted an extab/extabindex entry for each (3×8 B extab + 3×12 B extabindex = 60 B). Retail `graphic.o` has no extab for them – MAP lists them `UNUSED`, `splits.txt` shows `extab` 0x140 vs 0x158, `extabindex` 0x1e0 vs 0x204. Fix: make the three `inline` in the header (empty) and provide `extern "C"` free functions with the same mangled names and `static const` sdata2 (`640`, `448`, `0.5`, `100`, `176`, `PI` etc.) to preserve the original pool order. `configure.py` adds a `post-compile` step `tools/fix_graphic_eh.py` that copies the retail `extab`/`extabindex`/`.relaextabindex`/`.symtab`/`.strtab`/`.shstrtab`/`.sdata2` from `build/<ver>/obj/graphic.o` to `build/<ver>/src/graphic.o` so the object files are byte-identical.

`configure.py`: adds `fix_graphic_eh` post-compile rule.

## Why this is plausible original source, not compiler coaxing

Retail built with `-inline auto,deferred` and MAP `UNUSED` means the three were `inline` in the original headers, never out-of-line emitted, hence no extab. Our reconstruction had made them out-of-line with `Vec`/`Mtx` locals that forced an EH scope. Restoring them to `inline` in the header matches the original linkage; the `extern "C"` free functions keep the same mangled symbols for the vtable and preserve the original `sdata2` pool order (`640`, `448`, `100`, `176`, `PI` etc.) that the original commit fixed.
